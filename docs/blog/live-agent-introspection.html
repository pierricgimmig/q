q · design note

What the Agents Are Doing

Four agents on four tasks. The queue knows who claimed what and the percent each one last reported. It does not know whether the agent that has been quiet for six minutes is running a build or is stuck. This note is about closing that gap with what the agents already produce, and it ships the first piece.

The gap

With one agent you watch its terminal. With several you watch q top: a table of statuses, a PROG column with the percent each agent last reported, a PR link once one exists, and a list of recent changes. That answers where the work stands. It does not answer what is happening right now, which is the question you actually have when a row has not moved in a while.

Progress is self-reported and coarse. An agent that reports 40 percent and then spends twenty minutes on one command looks the same as one that crashed. The queue needs a signal that is cheap enough to be sent constantly and honest enough to be trusted.

What q already records

Every task carries an append-only, timestamped, actor-attributed log. The queue writes the state changes itself: task_claimed with the agent id, task_started with the branch, task_completed with the summary. The agent adds to it on purpose with q log ID "…", --progress 40, and artifacts; --attach report=PATH stores a report's text in the database so it outlives the file. Call this lane intent: what the agent says it is about to do, what it found, what it decided.

Intent is the right thing to ask an agent to write. It is the wrong place to get the record of what happened, because that record already exists and nobody had to ask for it.

What the harness writes without being asked

Claude Code keeps a JSONL transcript of every session as it runs, one record per line: each tool call with its name, its input and the one-line description the agent gave it, each result paired to its call by id, each model reply with token counts, and a flag on everything a sub-agent does. Codex keeps the same in its session rollouts with a different shape. Both are timestamped to the millisecond.

Claude Code also has hooks. PreToolUse and PostToolUse run a command with a JSON event on stdin: the session id, the transcript path, the tool name and its input. They are the push form of the same record, and they fire at exactly the moment you want to know about: the start of a tool call.

An earlier prototype on the Orbit side read a full transcript and posted it to Orbit's timeline: 1,419 records from one session, 173 tool calls drawn as spans, and a finding that one agent spent 74 percent of its working time in the model while its sibling on the same codebase spent 72 percent waiting on tools. That difference is invisible from a status table, and it is the difference between an agent that needs a faster model and one that needs a faster build. Call this lane action.

The design: three lanes, one place to look

intent · the task lognotes, progress, artifacts, state changes. Written by the agent, on purpose. Already in q.
action · the claim's activitythe tool call in flight, from the harness hook. Written by a script, constantly. This note ships it.
machine · the processesthe build, the tests, the benchmark: Orbit attached, or q exec spans. Bridge in q PRs #26 and #27.

The cheapest join between intent and action is one field on the claim. A claim already has a heartbeat, and a heartbeat already carries a timestamp. Give it a line of text:

q heartbeat 184 --claim-token $T --activity "Bash: cargo test --workspace"

The queue stores the line on the claim, trims it to 120 characters, and stamps it with the heartbeat time. q top and q ls grow an ACTIVITY column only while some agent has reported one, so a quiet queue keeps its compact table. q show prints it with its age. Over MCP, queue_heartbeat takes the same activity field. A heartbeat without one keeps the previous line, so an agent that only refreshes its lease does not erase what it said.

ID  STATUS       FEATURE  PROJECT  PRI  PROG  UPDATED   PR  TITLE                 ACTIVITY
 3  in_progress  (none)   q          0   40%  just now      Port the encoder      Bash: cargo test --workspace (8s)
 5  in_progress  (none)   q          0   10%  2m ago        Fit q top to the term  Read crates/q-cli/src/main.rs (6m)
 2  ready        (none)   q          1        1h ago        Compare encodings
 9  done         (none)   q          0  100%  5m ago    PR  Ship the parser

Read the second row again. Ten percent, last note two minutes ago, and its last activity was a file read six minutes ago. That is a stall you can see without opening anything, and it is exactly the case the status table could not show.

Filling it in for free

The agent does not have to remember to send it. tools/hooks/q-activity.sh is a Claude Code PreToolUse hook: it reads the event from stdin, turns it into Bash: cargo test --workspace or Read crates/q-cli/src/main.rs, and sends a heartbeat for the claim named by Q_TASK_ID and Q_CLAIM_TOKEN, or by a two-line .q-claim file in the working directory, against the default database, a Q_SERVER_URL server, or the file in Q_DB. With nothing set it exits quietly, so it is safe to install globally.

{ "hooks": { "PreToolUse": [ { "hooks": [
    { "type": "command", "command": "/absolute/path/to/q/tools/hooks/q-activity.sh" }
] } ] } }

What leaves the session is the tool name and the agent's own description of the call, cut at 120 characters. Command output, file contents and prompt text stay in the transcript. Every heartbeat also refreshes the lease, so an agent that is busy never expires; one that has gone silent is visible both by its stale activity and, eventually, by its expired claim.

What is proposed, not yet built

The transcript on the claim. The hook event includes transcript_path, the one thing a queue cannot discover on its own. q start --transcript PATH would let a bridge such as q orbit tail the full action lane under the agent's thread: every tool call as a span, the model's turns between them, sub-agents on their own threads, intent notes as marks over the spans that were running when they were written. The activity line is the thin version of this; the transcript is the full one, and both use the same join.

Following a task live. q log ID --follow would print new entries as they land, the way tail -f does, for the times you want one task's story rather than the whole table.

Silence as a signal. q top could colour an activity older than the agent's usual gap, so a stall stands out before anyone reads the age.

A Codex reader. Codex writes the same facts in a different shape. Its hook story is thinner, so the transcript tailer above matters more there.

Honest notes

Activity is still reported by something on the agent's machine. The hook makes it automatic, not authoritative: a harness with no hooks reports nothing, and a stale line means either a long tool call or a dead session; the age tells you which to check. Progress remains the agent's own estimate. The measurements quoted from the Orbit prototype are from two real sessions on one machine; they show the shape of the data, not a benchmark.
